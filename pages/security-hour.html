Lesson 1 · 4 minutes

Think like a defender (and an attacker)

CIA: what we protect

  • Confidentiality: only the right people read it (a tenant never sees another tenant's logs).
  • Integrity: nobody tampers with it (a block list can't be silently edited).
  • Availability: it works when needed (if the DNS resolver is down, the whole customer is offline).

Risk = threat × vulnerability × impact

Threat: someone or something that wants to hurt you (a phishing gang). Vulnerability: a weakness (an endpoint that skips the tenant check). Impact: what it costs if it happens. Fix the vulnerability with the highest product first, not the one that looks scariest.

Three habits

  • Least privilege: give each user, service and key the minimum access.
  • Defense in depth: assume one layer fails (UI hides the button and the API checks the role).
  • Fail closed: when unsure (unknown role, missing claim), deny.

The Delete button is hidden for READ_ONLY users in Angular. Is that access control?

UI gating is a convenience. The browser is the attacker's computer: they can call your API with curl. Real enforcement lives on the server.

A role string arrives that your code doesn't recognise. What should the permission check return?

Fail closed. A bug that denies too much gets reported in an hour; a bug that allows too much gets discovered in a breach report.

Lesson 2 · 8 minutes

How an attack actually runs

Almost every breach follows the same arc. Learn the stages: every security product (including yours) is built to break one or more of them.

StageWhat happensWhere DNS sees it
1 · DeliveryPhishing email with a link or attachment.User clicks micros0ft-login[.]com: a lookup for a 2-day-old look-alike domain.
2 · ExecutionMalware runs on the laptop.The dropper downloads its second stage: another lookup.
3 · Command & control (C2)Malware "phones home" for instructions, often every N seconds (a beacon).Regular lookups to a C2 domain, or hundreds of random-looking names (a DGA, domain generation algorithm).
4 · Lateral movementAttacker spreads to other machines with stolen credentials.Mostly internal; less DNS signal.
5 · Exfiltration / impactData stolen, or ransomware encrypts everything.Data smuggled out inside DNS queries (DNS tunnelling): long, high-entropy subdomains.

Why DNS is the choke point

Nearly every stage needs a name lookup before any connection is made. Block the lookup and the connection never happens, on every device, without installing anything on the device. That's the whole pitch of protective DNS.

MITRE ATT&CK

The industry's shared catalogue of attacker techniques (IDs like T1071.004 "Application Layer Protocol: DNS"). Threat reports and detections reference these IDs, so you'll see them in tickets.

At workDashboards that split blocks into "threat intel" vs "your policies" map directly to this table: intel catches stages 1–3 and 5, while customer policies (block categories, new domains) shrink the surface for stage 1.

A laptop looks up xk2v9q.biz, p8f3mz.biz, ty7wq1.biz… 300 times an hour. Most likely?

Random-looking, short-lived names in bulk are the signature of a domain generation algorithm: the malware tries many names until it finds the one the attacker registered today.

Which stage does blocking a phishing link's domain break?

Stage 1. The earlier you break the chain, the cheaper the incident.

Lesson 3 · 14 minutes

DNS, and what a protective resolver adds

Device"where is example.com?"
Recursive resolverprotective DNS lives here
Root"ask .com"
TLD (.com)"ask its nameserver"
Authoritative"93.184.215.14"

Records you'll see in logs

  • A / AAAA: name → IPv4 / IPv6
  • CNAME: alias to another name (chains can hide the real target)
  • MX mail, TXT text (verification, sometimes tunnelling), NS nameservers
  • Response codes: NOERROR, NXDOMAIN (doesn't exist: lots of these = DGA), SERVFAIL
  • TTL: how long the answer is cached. Very low TTLs + rotating IPs = "fast flux", a common malicious pattern.

Three verdicts

ALLOW answer normally. BLOCK refuse (NXDOMAIN or 0.0.0.0). REDIRECT answer with the IP of a block page that explains why, so users don't file "the internet is broken" tickets. A sinkhole is a redirect to a server that logs which infected machines still call home.

Passthrough / monitor mode: decide, log the decision, but allow anyway. That's how new customers trial safely.

Order of evaluation

Typically: customer allow list (always wins, to fix false positives) → customer block list → threat intel (malware, phishing, C2) → policy rules (categories like gambling, domain age, country, response IP) → default allow. Policies may be inherited down the tenant tree (partner → MSP → company).

Verdict lab: what signals would a resolver weigh?

A toy scorer (made-up weights, for intuition only). Type a domain or try a sample. Real engines combine intel feeds with signals like these.

Ways around protective DNS (know them)

  • DoH / DoT: browsers or malware send DNS over HTTPS to a public resolver, skipping yours. Defences: block known DoH endpoints, use the canary domain, enforce via agent.
  • Hard-coded IPs: no lookup at all. That's why IP-based enforcement (inline appliances) complements DNS.
  • Roaming laptops off the office network: hence an endpoint agent.

False positives are a product problem

Every wrong block is a support ticket and erodes trust. That's why allow lists win, why the block page shows a reason, why "review" requests exist, and why passthrough mode exists. Expect to build UI for all of these.

A domain is on a threat feed but the customer put it on their allow list. Usual result?

Allow lists exist to override false positives. The decision is still logged so the customer (and you) can audit it.

Why redirect to a block page instead of just returning NXDOMAIN?

UX and support: a page that says "blocked: phishing, request review" beats a browser error.

Which pattern suggests DNS tunnelling (data exfiltration)?

Data gets encoded into labels like dGhpcyBp….attacker.tld. Length + entropy + volume to one parent domain is the tell.

Lesson 4 · 8 minutes

Threat intelligence and IOCs

IOC: indicator of compromise

A concrete, matchable artefact: an IP, CIDR range, domain, URL, file hash (MD5/SHA-1/SHA-256), email address. Lists of these are what "lists", "feeds" and "indicators" mean in the product.

Pyramid of Pain

From easy for attackers to change to hard: hashes → IPs → domains → network artefacts → tools → TTPs (behaviour). Blocking hashes annoys attackers for minutes; detecting behaviour (like DGA patterns) costs them weeks.

Quality fields

  • Confidence / score: how sure (blocks often need score ≥ threshold)
  • First / last seen, expiry: IOCs go stale; an IP from last year may belong to a hospital now
  • Source: which feed said so (needed to debug false positives)
  • Category: phishing, malware, C2, spam…

Feeds and formats

STIX is the JSON format for describing threats; TAXII is the API to fetch STIX. Also: CSV/text lists, vendor APIs (OTX, ISAC sharing groups, EDR platforms). A "source" configurator in the UI usually means: URL + credentials + polling schedule + mapping into your indicator model.

Defang before you paste

Never paste a live malicious URL into chat or tickets: it becomes clickable and link scanners will fetch it. Write hxxps://evil[.]com/login and 203.0.113[.]7. Your UI should display IOCs defanged and copy them raw only on purpose.

Which IOC is cheapest for an attacker to change?

Bottom of the Pyramid of Pain: changing one byte gives a new hash.

Why do indicators need an expiry?

Cloud IPs and expired domains are recycled constantly. Stale intel blocks innocent services.

A security company's own portal is a prime target: it holds every customer's policies and logs. These are the mistakes that matter most, in the order you're likely to meet them.

Spot the bug (open each after you've guessed)

1 · An Angular guard 
canActivate: [() => {
  const role = localStorage.getItem('role');   // set at login
  return role === 'ADMIN';
}]

Bug: the role comes from localStorage, which the user can edit in DevTools (localStorage.setItem('role','ADMIN')). Fine for hiding UI, never for security. Fix: derive roles from the signed token's claims, and make sure the API enforces the same rule.

2 · A Spring repository 
@Query("SELECT i FROM Indicator i WHERE i.tenantId = :tenant AND i.value LIKE %:q%")
List<Indicator> search(@Param("tenant") long tenant, @Param("q") String q);

// controller
@GetMapping("/indicators/search")
List<Indicator> search(@RequestParam long tenant, @RequestParam String q) {
  return repo.search(tenant, q);
}

The query is actually parameterised (it uses :q), so that part is fine. The bug is the tenant: it comes from a request parameter, so any user can read any tenant's indicators (IDOR). Fix: take the tenant from the authenticated principal, never from the request.

3 · A "test resolver" endpoint 
@GetMapping("/tools/dns-test")
String test(@RequestParam String server, @RequestParam String name) {
  return rest.getForObject("http://" + server + "/resolve?name=" + name, String.class);
}

Bug: SSRF. server=169.254.169.254/latest/meta-data/iam makes your server fetch its own cloud credentials. Fix: accept a server key mapped to an allowlisted URL in config, require an admin role, and set timeouts.

At workCode reviews in security companies get asked "which tenant can see this?" on every endpoint. Ask it of your own PRs first, and add one test per role: allowed, denied, other tenant.

You find a database password in application.yml on main. First step?

Deleting doesn't remove it from history or from anyone's clone. Rotation is the only real fix; cleanup comes after.

Which is the strongest tenant check?

Anything the client sends can be changed. The verified token is the source of truth on the server.

Why is a token in a URL query string dangerous?

Any of those places can leak a live session. Hand-offs should use one-time codes exchanged server-side.

Lesson 6 · 7 minutes

Cloud basics and what to do in an incident

AWS shared responsibility

AWS secures the data centres and hypervisors. You secure everything you configure: IAM, security groups, S3 bucket policies, patching your EC2 images, database access, secrets.

The checklist that prevents most cloud incidents

  • IAM roles with least privilege; no long-lived access keys on laptops
  • RDS (Postgres) in private subnets, never public; TLS on
  • S3 private by default; share with presigned URLs that expire
  • Secrets in Secrets Manager / SSM, rotated
  • CloudTrail + CloudWatch logs on; alerts on root login
  • Security groups: no 0.0.0.0/0 on admin ports

If you think something is wrong

  1. Don't destroy evidence: don't wipe, reboot or "clean up".
  2. Report early to your lead / security channel, even if unsure.
  3. Contain when told to: rotate the key, disable the user, block the domain.
  4. Write the timeline as you go (UTC times).
  5. Blameless post-mortem: fix the system, not the person.

You need to give a customer a download of their export file in S3. Best way?

Presigned URLs grant access to one object, for a short time, without sharing credentials.

You accidentally pushed an AWS key to a public repo and deleted it 2 minutes later. Safe?

Automated scanners watch public GitHub in real time. Assume it's compromised.

Logs carry the reason and the matching rule. With inheritance, check which level (partner, MSP, company) the rule came from.

Which statement is true?

DNS only sees lookups. Layers cover each other's gaps: defense in depth again.
