Layer 1 · 20 minutes

How bytes travel

Address + port

An IP address finds the machine; a port finds the program on it. 203.0.113.10:443 = "the HTTPS server on that machine". Postgres listens on 5432, DNS on 53, HTTPS on 443, SSH on 22.

Private ranges (10.x, 172.16–31.x, 192.168.x) only work inside a network. NAT lets many private machines share one public IP on the way out.

TCP vs UDP

TCP: a phone call. Handshake first (1 round trip), delivery guaranteed and in order. HTTP, Postgres and SSH use it.

UDP: a postcard. No handshake, no guarantee, very fast. Classic DNS uses UDP: one small question, one small answer. If it's lost, ask again.

One HTTPS request, in round trips

  1. DNS: name → IP (often cached: 0 trips)
  2. TCP handshake: 1 round trip
  3. TLS handshake: 1 more (TLS 1.3)
  4. HTTP request → response: 1 more

So a fresh connection to a server 100 ms away costs ~300 ms before the first byte. That's why latency matters more than bandwidth, and why reusing connections (keep-alive, connection pools) matters so much.

Load balancers: L4 vs L7

Layer 4 (AWS NLB) forwards TCP/UDP connections without reading them: very fast, keeps the client IP, works for DNS. Layer 7 (AWS ALB) reads HTTP: routes /api/billing to one service and /api/lists to another, ends TLS, adds X-Forwarded-For. Both run health checks and stop sending traffic to sick servers.

CDN

Copies of static files (the Angular bundle, images) kept in hundreds of locations close to users (AWS CloudFront). The browser downloads main.js from 10 ms away instead of from your origin server. CDNs use anycast too.

Layer 1 · 15 minutes · the question from your manager

Anycast: one address, many places

Unicast (normal)

One IP address belongs to one server in one place. Everyone in the world travels to that place.

Anycast

The same IP is announced from many data centres at once, using BGP, the protocol internet routers use to tell each other "I can reach this address". Each router picks the shortest network path, so every user lands on the nearest copy.

Failover for free

If a site goes down, it withdraws its BGP announcement. Within seconds routers forget that path and send traffic to the next nearest site. Customers change nothing: the IP they configured still works.

Why protective DNS uses it

  • Every DNS lookup waits for the answer: 10 ms vs 250 ms is felt on every page load.
  • Customers configure one or two IPs on routers worldwide. Anycast is the only way one IP can be close to everyone.
  • A site outage or DDoS is absorbed: traffic spreads over the remaining sites.
  • DNS over UDP is a single packet each way, so it never cares which site answered the previous query.

The fine print (sounds senior in meetings)

  • "Nearest" means the shortest BGP path, not the shortest distance. A user in one country can land on a far site because of how their ISP peers.
  • Long-lived TCP connections can break if routes change mid-connection. Fine for DNS and HTTP, which are short.
  • Every site must hold the same policy data, so policy changes in the portal must be pushed to all sites quickly (see the system map below).
  • In AWS: Route 53, CloudFront and Global Accelerator are anycast services. You can also bring your own IP range and announce it.
What to say to your manager

"Anycast means the same IP is announced over BGP from many locations, so routers send each client to the nearest one. That's why our customers can point at one resolver IP and still get low latency everywhere, and why a site can drop out without anyone reconfiguring: its route is withdrawn and traffic shifts to the next site. The catch is that every site needs the same policy data, and 'nearest' is by BGP path, not by distance."

5 minutes

Explain it back

A customer in Singapore and one in London both use resolver IP 198.51.100.53. What happens?

That's anycast: same IP, many announcements, routers choose the shortest path. No DNS trick is involved; it happens at the IP routing level.

The Frankfurt site goes down. What do Frankfurt-area customers need to change?

Failover happens in the routing layer within seconds. That's a big part of why anycast is used for DNS.

An admin blocks a domain in the portal. Why might a query 2 seconds later still be allowed?

The control plane (portal → API → Postgres) and the data plane (resolvers with cached policy) are separate. Propagation time is a real product metric.

Which load balancer would sit in front of a UDP DNS service?

ALB only speaks HTTP(S). DNS is UDP (and TCP for big answers), so you need a layer-4 balancer.

Your Spring Boot API runs 500 small Postgres queries for one page. Each takes 1 ms in the same region. What's the problem?

Round trips add up. Layer 3 teaches how to see this in logs and fix it with joins or batch queries.
